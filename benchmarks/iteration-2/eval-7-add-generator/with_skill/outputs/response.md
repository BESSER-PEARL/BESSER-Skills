# Adding a GraphQL Generator to BESSER

Adding a generator is the most common BESSER contribution. There are two ways to start: use the bundled scaffold script (recommended) or do it by hand. Either way, you end up implementing the same 6 steps.

## Fast path: scaffold the package

BESSER ships a scaffold script that writes a working stub (generator class + Jinja template + pytest) you can run immediately:

```bash
python scripts/scaffold_generator.py graphql ~/code/BESSER
```

This generates:

```
besser/generators/graphql/__init__.py
besser/generators/graphql/graphql_generator.py
besser/generators/graphql/templates/graphql_template.py.j2
tests/generators/graphql/__init__.py
tests/generators/graphql/test_graphql_generator.py
```

The class name is derived automatically: `graphql` → `GraphqlGenerator`. Run the generated test right away to confirm wiring before adding real logic:

```bash
python -m pytest tests/generators/graphql/
```

The scaffold does NOT do everything — you still must (1) implement real logic, (2) register in the web-editor config, and (3) add docs. Those are covered below.

## The 6 steps in detail

### Step 1 — Create the generator package

If doing it by hand (the scaffold does this for you), the layout is:

```
besser/generators/graphql/
  __init__.py               # export: from .graphql_generator import GraphQLGenerator
  graphql_generator.py      # the generator class
  templates/                # Jinja2 templates
    graphql_template.j2
```

`__init__.py`:

```python
from .graphql_generator import GraphQLGenerator

__all__ = ["GraphQLGenerator"]
```

A good starting point to copy from is a simple existing generator such as `python_classes/`.

### Step 2 — Implement `GeneratorInterface`

Your generator subclasses `besser.generators.GeneratorInterface` and implements `generate()`:

```python
# besser/generators/graphql/graphql_generator.py
"""GraphQLGenerator — generates a GraphQL schema (SDL) from a BESSER B-UML model."""

import os
from jinja2 import Environment, FileSystemLoader

from besser.generators import GeneratorInterface


class GraphQLGenerator(GeneratorInterface):
    """Generates a GraphQL schema from a B-UML domain model."""

    def __init__(self, model, output_dir: str = None):
        super().__init__(model, output_dir)

    def generate(self):
        templates_path = os.path.join(os.path.dirname(__file__), "templates")
        env = Environment(
            loader=FileSystemLoader(templates_path),
            trim_blocks=True,
            lstrip_blocks=True,
        )
        template = env.get_template("graphql_template.j2")
        output = template.render(
            classes=self.model.get_classes(),
            associations=self.model.associations,
        )
        file_path = self.build_generation_path("schema.graphql")
        with open(file_path, "w", encoding="utf-8") as f:
            f.write(output)
```

Key requirements (these are non-negotiable for a clean PR):

- Call `super().__init__(model, output_dir)` — this sets up `self.model` and `self.output_dir`.
- Use `self.build_generation_path(filename)` to get the correct output file path (or `self.build_generation_dir()` for just the directory).
- Keep templates in the `templates/` subfolder next to the generator.
- **Output must be deterministic** — the same model produces byte-identical output every run (no timestamps, no random ordering, no nondeterministic set iteration). This is enforced and tested.
- Reusable helpers go in `besser/utilities/`, NOT inside the generator (don't duplicate logic).

### Step 3 — Write the Jinja2 template

You'll map B-UML classes to GraphQL types. A starting `graphql_template.j2`:

```jinja2
{# Generated by BESSER GraphQLGenerator #}
# Generated by BESSER GraphQLGenerator
{% for cls in classes %}
type {{ cls.name }} {
  {% for attr in cls.attributes %}
  {{ attr.name }}: {{ attr.type.name }}
  {% endfor %}
}

{% endfor %}
```

(You'll want to expand this with proper B-UML-type → GraphQL-scalar mapping, e.g. `StringType` → `String`, `IntegerType` → `Int`, plus relationship fields derived from `associations` and multiplicities for list vs. single and nullability.)

Note: the special delimiter trick (`variable_start_string="[[", variable_end_string="]]"`) is only needed when your template language collides with Jinja's `{{ }}` (e.g. JSX/React). Plain GraphQL SDL doesn't need it.

### Step 4 — Register in the web-editor backend

Edit `besser/utilities/web_modeling_editor/backend/config/generators.py`:

```python
from besser.generators.graphql import GraphQLGenerator

GENERATORS = {
    # ... existing generators ...
    "graphql": GeneratorInfo(
        generator_class=GraphQLGenerator,
        output_type="file",            # "file" for single file, "zip" for multi-file
        file_extension=".graphql",     # output extension
        category="backend",            # grouping label in the editor
        requires_class_diagram=True,   # True — GraphQL schema needs a DomainModel
    ),
}
```

Also update `get_filename_for_generator()` in the same file so the editor serves the right filename (e.g. `schema.graphql`).

### Step 5 — Write tests

Create `tests/generators/graphql/test_graphql_generator.py`:

```python
import os
import pytest
from besser.BUML.metamodel.structural import (
    DomainModel, Class, Property, StringType, IntegerType,
)
from besser.generators.graphql import GraphQLGenerator


@pytest.fixture
def domain_model():
    """Build a small inline test model."""
    name_prop = Property(name="name", type=StringType)
    age_prop = Property(name="age", type=IntegerType)
    person = Class(name="Person", attributes={name_prop, age_prop})
    return DomainModel(name="TestModel", types={person})


def test_generate_creates_output_file(domain_model, tmp_path):
    gen = GraphQLGenerator(model=domain_model, output_dir=str(tmp_path))
    gen.generate()
    assert os.path.exists(tmp_path / "schema.graphql")


def test_generate_contains_type_and_fields(domain_model, tmp_path):
    gen = GraphQLGenerator(model=domain_model, output_dir=str(tmp_path))
    gen.generate()
    content = (tmp_path / "schema.graphql").read_text()
    assert "type Person" in content
    assert "name" in content
    assert "age" in content
```

What to test for a generator (from the skill's conventions):

- **File existence** — the expected output file is created.
- **Key content** — class/type names, field names, and relationship mappings appear in output. Assert specific content, not just that a file exists.
- **Edge cases** — empty model, deep inheritance, many-to-many associations.
- **Type mapping** — verify B-UML types render as the correct GraphQL scalars.
- (Optional) **Determinism** — generate twice and assert the two outputs are identical.

Test patterns used throughout the codebase:

- Use the `tmp_path` (or `tmpdir`) fixture for output dirs — auto-cleaned by pytest. If you don't use it, clean up with `shutil.rmtree()` in a `try/finally`.
- Build small inline models as fixtures; don't depend on external files.
- Test files named `test_*.py`, functions named `test_*`.
- Test error conditions with `pytest.raises(...)`.

Run them:

```bash
python -m pytest tests/generators/graphql/ -v
```

### Step 6 — Document

Create `docs/source/generators/graphql.rst`:

```rst
GraphQLGenerator
================

The GraphQLGenerator produces a GraphQL schema (SDL) from a B-UML domain model.

Prerequisites
-------------

- BESSER installed
- A structural (class) B-UML model

Usage
-----

.. code-block:: python

   from besser.generators.graphql import GraphQLGenerator

   gen = GraphQLGenerator(model=my_model, output_dir="./output")
   gen.generate()

Output
------

The generator produces a single file ``schema.graphql`` containing one GraphQL
``type`` per B-UML class.
```

Then add `graphql` to the generators index in `docs/source/generators.rst`. Build the docs to confirm:

```bash
cd docs
make.bat html      # Windows (you're on Windows)
# open docs/build/html/index.html
```

## Finishing up: commit + PR

- Branch: `git checkout -b feature/add-graphql-generator`
- Conventional Commit message, e.g. `feat: add GraphQL schema generator`
- Run the full suite locally before pushing (there is **no CI test workflow** — local pytest is the gate):
  ```bash
  python -m pytest
  ```
- Build the docs (`cd docs && make.bat html`), rebase on latest `master`, push, and open a PR against `master`. Fill in the PR template (description, tests executed, context). Merge needs two maintainer approvals (one suffices after 14 days).

## Pitfalls to avoid

1. **Determinism** — no timestamps/random/unordered output; same model → same bytes.
2. **No duplicated logic** — shared helpers belong in `besser/utilities/`, not the generator.
3. **Update docs** — a backend/config change needs matching `docs/source/` updates.
4. **Don't touch the frontend submodule** unless explicitly required (UI changes go to the upstream WME repo). Registering in the backend `config/generators.py` is enough to expose the generator in the editor.
5. **Clean up resources** — use `tmp_path` or `try/finally` around temp dirs and file handles.
